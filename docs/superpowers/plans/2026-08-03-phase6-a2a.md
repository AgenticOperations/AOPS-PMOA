# Phase 6: Agent-to-Agent Payment Implementation Plan

> **For Claude:** REQUIRED: Use superpowers:subagent-driven-development (if subagents available) or superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax.
>
> **Read `2026-08-03-scope-and-cuts.md` first.**

**Goal:** Let one agent pay another with a signed on-chain spending ceiling that decrements per payment, expires on its own, and can be revoked instantly — then run a real fleet that exercises it end to end.

**Architecture:** Permit2 (already deployed at its canonical address on Arc) provides the ceiling. An operator signs one `PermitSingle` per payer→payee pair; the paying agent draws against it with `transferFrom`; `lockdown()` revokes. Funds never leave the payer's wallet, so Phase 3's balance ceiling still holds. Each earning agent runs a small paid HTTP service, because x402 is request/response — you cannot push USDC at an idle wallet.

**Tech Stack:** `viem` (already a dependency), Permit2 at `0x000000000022D473030F116dDEE9F6B43aC78BA3`, x402 tooling pinned to `x402-foundation/x402`.

**⚠️ GATE — read before starting:** this phase is gated on Phase 0 spike **S4**. If Permit2 cannot interact with Arc's native-USDC ERC-20 view (which truncates), **stop** and take the fallback in the box below. Do not attempt to work around it mid-phase.

> **S4 fallback:** Lane 2 drops to per-payment `exact` authorizations — each agent-to-agent payment is signed individually, with no standing ceiling and no drawdown. The target tier drops **T3 → T4**. Agent-to-agent payment still works; the *scoped delegation* claim does not. Record this in `docs/decisions.md` and remove the delegation claim from the deck.

## Context you need before starting

**This is entirely greenfield.** Zero occurrences of Permit2, ERC-8183, or ERC-8004 anywhere in the codebase. Nothing here modifies a working flow — it is all new.

**Why Permit2 rather than escrow.** Permit2 gives a signed ceiling with incremental drawdown, a hard expiry, and instant revocation — and because funds stay in the payer's wallet, Phase 3's on-chain balance ceiling continues to bind. Escrow (ERC-8183) would park funds in a third-party contract, add ~5 on-chain transactions per job, and depend on an unaudited Draft EIP. Per the manifest's D2b rule, intra-fleet payments are **Mode 1** — trust already exists between agents answering to the same treasury, so escrow adds cost for no trust gain.

**The honest tradeoff to state plainly:** because funds remain with the payer, the **payee carries collection risk** — the payer could spend that balance elsewhere before the payee draws. Inside a fleet whose payer spending we already gate, that is the correct place for the risk to sit. Do not claim otherwise.

**Two hard constraints:**
- **EOA only.** Gateway verifies signatures off-chain via `ecrecover` and Nanopayments is EOA-only. Phase 2's migration 0024 and Phase 3's table CHECK already enforce this.
- **The payee must expose an HTTP endpoint.** x402 is request/response. This is why Task 4 exists and why the manifest calls it real work, not config.

**What K-3 actually costs.** The change manifest says twice that the agent runtime harness is the largest hidden cost, and it is right. Everything in Phases 1–5 is control-plane work on an existing codebase. This is building processes that make real decisions. Budget accordingly.

- [ ] **Step 1: Write the migration**

```sql
-- 0028_permit2_delegations.sql
-- Permit2 ceiling + drawdown accounting. The on-chain allowance is the
-- authority; these rows mirror it so the control plane can reason about
-- remaining headroom without an RPC call per decision.

CREATE TABLE IF NOT EXISTS agent_delegations (
  id text PRIMARY KEY,
  org_id text NOT NULL REFERENCES orgs (id) ON DELETE RESTRICT,
  payer_agent_id text NOT NULL REFERENCES agents (id) ON DELETE RESTRICT,
  payee_agent_id text REFERENCES agents (id) ON DELETE RESTRICT,
  payee_address text NOT NULL,
  mode text NOT NULL CHECK (mode IN ('test', 'live')),
  chain text NOT NULL CHECK (chain IN ('base', 'arbitrum', 'polygon', 'optimism', 'avalanche', 'arc')),
  token_address text NOT NULL,
  ceiling_usdc numeric(20, 6) NOT NULL CHECK (ceiling_usdc > 0),
  drawn_usdc numeric(20, 6) NOT NULL DEFAULT 0 CHECK (drawn_usdc >= 0),
  expires_at timestamptz NOT NULL,
  permit_nonce bigint NOT NULL,
  signature text,
  status text NOT NULL DEFAULT 'pending'
    CHECK (status IN ('pending', 'active', 'exhausted', 'expired', 'revoked')),
  approved_by text NOT NULL,
  created_at timestamptz NOT NULL DEFAULT now(),
  updated_at timestamptz NOT NULL DEFAULT now(),
  CHECK (drawn_usdc <= ceiling_usdc),
  UNIQUE (payer_agent_id, payee_address, mode, chain, permit_nonce)
);

CREATE INDEX IF NOT EXISTS agent_delegations_active_idx
  ON agent_delegations (org_id, payer_agent_id, mode, chain, status);

-- Every drawdown, append-only. The on-chain allowance decrements; this is
-- the local record of why.
CREATE TABLE IF NOT EXISTS agent_delegation_drawdowns (
  id text PRIMARY KEY,
  delegation_id text NOT NULL REFERENCES agent_delegations (id) ON DELETE RESTRICT,
  amount_usdc numeric(20, 6) NOT NULL CHECK (amount_usdc > 0),
  tx_hash text,
  status text NOT NULL DEFAULT 'submitted'
    CHECK (status IN ('submitted', 'confirmed', 'failed')),
  created_at timestamptz NOT NULL DEFAULT now()
);
```

### Task 2: Permit2 module `[K-8, K-12]`

- [ ] **Step 1: Write the failing test**

```ts
describe('Permit2 delegation', () => {
  it('rejects a drawdown that exceeds the remaining ceiling', async () => {
    const { delegationId, pool } = await setupDelegation({
      ceilingUsdc: '10.00', drawnUsdc: '8.00',
    });
    await expect(drawDown(pool, { delegationId, amountUsdc: '3.00' }))
      .rejects.toThrow(/ceiling/);
  });

  it('decrements the remaining ceiling across successive drawdowns', async () => {
    const { delegationId, pool } = await setupDelegation({ ceilingUsdc: '10.00' });

    await drawDown(pool, { delegationId, amountUsdc: '3.00' });
    await drawDown(pool, { delegationId, amountUsdc: '2.00' });

    const row = await pool.query('SELECT drawn_usdc FROM agent_delegations WHERE id = $1', [delegationId]);
    expect(Number(row.rows[0].drawn_usdc)).toBe(5);

    const draws = await pool.query(
      'SELECT count(*) FROM agent_delegation_drawdowns WHERE delegation_id = $1', [delegationId],
    );
    expect(Number(draws.rows[0].count)).toBe(2);
  });

  it('rejects a drawdown against an expired delegation', async () => {
    const { delegationId, pool } = await setupDelegation({
      ceilingUsdc: '10.00', expiresAt: new Date(Date.now() - 1000),
    });
    await expect(drawDown(pool, { delegationId, amountUsdc: '1.00' }))
      .rejects.toThrow(/expired/);
  });

  it('rejects a drawdown after revocation', async () => {
    const { delegationId, pool } = await setupDelegation({ ceilingUsdc: '10.00' });
    await revokeDelegation(pool, { delegationId });
    await expect(drawDown(pool, { delegationId, amountUsdc: '1.00' }))
      .rejects.toThrow(/revoked/);
  });

  it('serializes concurrent drawdowns so the ceiling cannot be overdrawn', async () => {
    const { delegationId, pool } = await setupDelegation({ ceilingUsdc: '10.00' });
    const results = await Promise.allSettled([
      drawDown(pool, { delegationId, amountUsdc: '6.00' }),
      drawDown(pool, { delegationId, amountUsdc: '6.00' }),
    ]);
    expect(results.filter((r) => r.status === 'fulfilled')).toHaveLength(1);
  });
});
```

- [ ] **Step 2: Run to verify it fails, then implement `permit2.ts`**

Four operations:

- `buildPermitSingle(...)` — construct the EIP-712 `PermitSingle` payload (`amount` uint160, `expiration` uint48, `nonce` uint48).
- `recordSignedDelegation(...)` — persist the signature, mark `active`.
- `drawDown(...)` — inside a transaction with `SELECT ... FOR UPDATE` on the delegation row: check status, expiry, and `drawn + amount <= ceiling`; insert a drawdown row; call `transferFrom`; update `drawn_usdc`. The row lock is what makes the concurrency test pass.
- `revokeDelegation(...)` — call Permit2 `lockdown()`, mark `revoked`.

Local accounting must never be treated as authoritative — the on-chain allowance is. If they disagree, trust the chain and reconcile.

- [ ] **Step 3: Verify against real Arc testnet**

Using S4's verified path:
1. Operator signs a **$5.00** ceiling for payer→payee.
2. Draw **$1.00** three times.
3. Read the on-chain allowance after each and confirm it decremented.
4. Call `lockdown()`; confirm the allowance is zero and a fourth draw fails.
5. Confirm the payer's **balance never left their wallet** until each draw.

Record every tx hash in `docs/spike-results.md`.
